重启网关不会丢失代理状态。会话、转录、计划任务、后台任务记录以及排队中的外发消息都保存在磁盘上，而在轮次中途被中断的工作会被检测到，并在网关重新启动后自动恢复。无需人工干预，也没有任何需要配置的内容：恢复始终启用。

本页介绍了重启后哪些内容会保留、如何检测中断的工作，以及自动恢复看起来是什么样子。

## 重启后会保留什么

| 状态                         | 存储                                        | 重启后的行为                                                      |
| ----------------------------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| 会话历史                     | 每个代理的 SQLite 数据库                   | 不受影响；会话从已存储的转录继续                                   |
| 被中断的主会话轮次           | 每个代理的 SQLite 会话行和转录               | 在启动几秒后自动恢复                                               |
| 子代理运行                   | SQLite（共享状态数据库）                    | 启动时恢复注册表；中断的运行会继续                                |
| 后台任务                     | SQLite（共享状态数据库）                    | 启动时重新对账；孤立的运行会被恢复或标记为丢失                    |
| 排队中的出站投递             | SQLite 投递队列                             | 重启后清空；未投递的回复会重试                                    |
| 定时（cron）任务             | SQLite cron 存储                            | 计划会保留；调度器在启动时重新设防                            |
| 重启继续                     | SQLite 重启哨兵                            | 向请求重启的会话发送一次性的后续消息                              |

## 优雅重启会先进行排空

请求的重启（`openclaw gateway restart`、需要重启的配置变更，或网关更新）不会立即终止正在进行中的工作。网关会停止接受新的工作，然后等待活跃的代理回合和后台任务完成，最长等待一个排空预算（默认 5 分钟）。因此，大多数重启根本不会中断任何内容。

只有无法在排空预算内完成的工作（或任何被强制重启或崩溃中断的运行）才会被终止——并且在此之前，每个受影响的会话都会被标记为可恢复。

## 中断工作如何被检测

三个相互补充的机制会标记那些回合未能完成的会话：

- **在 Control UI 接入时：**对于现有主会话中的普通文本回合，网关会追加用户消息，将会话标记为运行中，并在返回 `started` 确认之前，在一次 SQLite 事务中记录其仅转录传递声明。
  命令、附件、每回合覆盖、待处理传递、先前的中止提示、插件拥有的会话，以及带有执行钩子的回合，都会保留各自专用的接入路径。
- **在关闭时：**在重启排空期间，任何处于活动运行状态的会话都会在运行被中止之前，在会话存储中被标记上恢复标记。
- **在启动时：**网关会扫描会话存储，查找那些仍然声称正在运行、但在新进程中已经没有活动拥有者的会话。这可以捕获硬崩溃以及没有执行任何关闭代码的终止情况。过期的转录锁文件也会在同一时间被清理。

## 自动恢复

启动后几秒钟，网关会重新分派每个已标记的会话，并附带一条合成的系统消息，告诉代理它的上一轮因重启而中断，并要求它从现有对话记录继续。若已经生成了最终回复但尚未送达，则其文本也会一并包含进去，这样代理就可以直接发送该回复，而无需重新执行工作。恢复最多重试 3 次，并采用指数退避。每次重试都会复用同一个持久化分派标识，因此，即使连接失败的情况含糊不清，也不会对同一次恢复发起两次。已完成且不可恢复的 Control UI 回合也会保留有界的持久化幂等墓碑，使重新连接的 outbox 能够在不重新执行请求的情况下将其退役。

在恢复之前，网关会检查对话记录末尾是否可以安全继续。如果不安全（例如该回合以一个过期的待审批状态结束），系统不会盲目重跑该会话；代理会改为发布一条简短通知，要求用户重新发送上一条请求。对于 WebChat，这条通知会直接写入会话历史，因此在重新连接后仍然可见。

OpenClaw 还可以重建被中断的只读 [代码模式](/reference/code-mode) 工作。代码模式会将这些运行标记为可重启安全，并在执行前拒绝有副作用的 catalog 工具或插件命名空间。如果重启落在 `wait` 控制点上，新网关会根据其对话记录重建该回合，并强制重建后的执行保持可重启安全，即使模型省略或清除了该标记。主机将整个重建回合过滤为经过审计的只读核心工具，以及明确可安全重放的插件工具，即使在重启后代码模式已被禁用也是如此。具有副作用的工作仍然由重新发送通知来保护，而不是冒着重复写入的风险。

### 子代理

子代理运行会持久化到共享的 SQLite 状态数据库中，因此子代理注册表会随进程一同保留。启动时会恢复注册表，并携带原始任务上下文继续已中断的子代理会话。适用两个安全阀：

- 若运行在 2 小时之前被中断，则会直接完成归档而不是恢复，因此整夜停机的网关不会让过时的工作“复活”。
- 如果某个会话反复恢复失败，则会被标记为卡死并加上墓碑，以免恢复无限循环。

### 后台任务

[后台任务注册表](/automation/tasks) 由 SQLite 支持，并会在启动时以及定期周期内进行协调：已完成运行记录的持久化结果会被恢复，而其所属进程已消失的运行会在宽限期后被标记为丢失，而不是永远挂起。

### 代理请求的重启

当代理自身触发重启时（应用配置更改、更新网关，或显式重启请求），在进程退出前会先将一个重启哨兵写入 SQLite。启动后，网关会将结果回传到发起该操作的聊天，并派发一个一次性的续接回合，让代理在相同的频道和线程中，精确地从离开的地方继续。

## 安全阀与可观测性

- **崩溃循环断路器：** 5 分钟内出现 3 次非正常启动会触发断路器，在下一次启动时抑制自动启动的侧边服务，从而避免网关崩溃后自我放大。待非正常启动时间窗口自然过期后即可恢复。
- **指标：** 恢复活动通过
  [Prometheus](/gateway/prometheus) 导出为 `openclaw_session_recovery_total` 和
  `openclaw_session_recovery_age_seconds`。
- **日志：** 恢复决策会记录在
  `main-session-restart-recovery` 和 `subagent-interrupted-resume`
  子系统下。

## 未恢复的内容

- 因为已由其他所有者处理而被排除在主会话恢复之外的会话：子代理会话（子代理恢复）、cron 会话（调度器按计划重新运行）以及 ACP 管理的会话（已连接的 IDE 或客户端拥有恢复权）。
- 其记录尾部无法安全继续的会话；这些会收到上文所述的重新发送通知，而不是静默重跑。
- 从未被接纳的工作：在排空窗口期间到达的消息会被以明确的重启错误拒绝，而不是静默排队到一个即将终止的进程中。
