## <a id="runners"></a> 运行器

### <a id="testbox-spending-limits"></a> Testbox 支出限额

集中、常规、通用、高内存、ARM、构建工件和 Windows Testbox 工作流程共享 32 个并发槽。在 Blacksmith 作业符合资格之前，GitHub-hosted 准入作业会验证租约 ID、运行程序和运行时。调度在其分配的时隙中等待，而不取消活动租约。使用GitHub的`queue: max`，每个槽最多保留100个待处理请求；较新的请求不会取代较早的服务员。当槽的队列已满时，GitHub 会取消其他请求。当每个作业进入槽队列时进行排序，而不是工作流调度时间。哈希冲突仍然可能导致其他槽位未使用；这是一个上限，而不是 32 台繁忙机器的承诺。

准入将在工作流程创建 60 分钟后过期。这种有界队列允许让等待的客户端在超过前十分钟截止时间的饱和状态下幸存下来，而无需接受任意旧的放弃请求。它是一个操作界限，而不是测量的队列百分位或客户端仍在等待的证据：委托的预热合约不会向这些工作流公开任何请求者心跳，并且 SSH 活动仅在运行程序分配后可用。当运行程序启动时，等待 60 分钟或更长时间的请求在结账或补充之前会失败；它仍然会产生运行者的启动成本。比绑定更年轻的废弃请求仍然可以进行水合，因此仍然需要调用者清理。这不会立即删除排队的作业，也不会在分配运行程序时重置时钟。一旦请求通过该检查，结帐和水合就不会重新检查队列年龄。它们仍然受到作业超时和空闲限制的限制。通过确切的 ID 停止废弃的租约，而不是让预热挂起。对于排队租约，还要验证其支持操作运行是否已终止； Blacksmith 的 `completed` 租赁状态本身并不能证明排队运行已取消。在取消放弃的运行之前，匹配准入作业日志中的确切 `TESTBOX_ID`；其标题或创作时间不够。如果该任务拥有的运行仍处于挂起状态，请使用 `gh run cancel <run-id> --repo openclaw/openclaw` 并确认其最终状态。如果租约到运行匹配不可用，请报告未解决的清理，而不是取消猜测的运行。当池已满时，不要在循环中重试。

如果准入作业无法读取其运行的 GitHub 操作，它将拒绝准入并报告 HTTP 状态、修复的错误分类以及经过验证的 GitHub 请求 ID 和速率 limit/retry 标头（如果可用）。在现有的 15 秒请求期限内，错误主体限制为 8 个 KiB；原始响应消息和正文永远不会被记录。裸露的 `403` 报告为 `forbidden`，不假定为权限或速率限制失败。使用请求 ID 调查原始 GitHub 响应；后来的成功请求并不能解释之前的拒绝。在稍后请求之前兑现 `retry-after`（秒）。当 `x-ratelimit-remaining=0` 时，等待 `x-ratelimit-reset`（UTC 纪元秒）。准入不会重试或更改令牌权限，并且失败的请求仍然需要调用者清理。

空闲请求的上限为 15 分钟。现有的 Testbox 监视器继续保护活动的 SSH 命令。任务完成后停止保留的租约；空闲限制不能替代调用者清理。

常规远程校样采用16级。显式高内存工作流程只能使用共享 32 个插槽中的 4 个；它不会再添加四个插槽。正常租约也可以占用这些插槽，因此哈希冲突可能会将高内存工作排队到其上限以下。完成后停止拥有的租约，而不是请求新的 ID 来避开繁忙的时段。

仅将 32 类用于具有测量内存需求的命名命令、经过验证的较小运行程序 OOM 或显示较低总计费成本的受控比较。分配前记录证据。显式的全套 Testbox PR 门保留了此例外；普通遥控指令和变闸采用16级。选型参见[远传](/reference/test/remote-proof#testbox-runner-sizing)。失败的测试、队列延迟或一般超时都不能证明升级是合理的。

一般证明默认为 60 分钟（包括水合作用）。现有的 `timeout_minutes` 输入可以请求更短的期限或明确将已知的长证明延长至 240 分钟；较大的值在分配之前会失败。本机 Blacksmith 预热不会公开任意工作流程输入，并且 Crabbox `--ttl` 不会强制执行 Testbox 生命周期。 GitHub 作业超时是挂钟限制。

10 月 1 日的规模审核倾向于 16 级，而不是全面默认的 8 级。在过去 7 天中，5,521 次 32 级运行的中位寿命为 31 分钟，p95 为 108 分钟。内存采样器返回 4,436 次合格运行；采样的 [median](https://github.com/openclaw/openclaw/actions/runs/36588824988/job/109476238445) 和 [p75](https://github.com/openclaw/openclaw/actions/runs/36593802388/job/109493424473) 峰值分别为 6.2 和 12.8 GiB 与 8 类观察到的 7.66 GiB。在这些采样峰值处，总 RAM 减去可用 RAM 为 6.8 和 13.4 GiB，因此可回收缓存并不能解释较小类别的风险。单独的 6,199 个运行的 16 类人群还包括 25 个 OOM- 受影响的工作；这些人群的规模比较不受控制。

工作持续时间包括水合作用、命令和空闲保留。采样的 [31- 分钟作业 ](https://github.com/openclaw/openclaw/actions/runs/36630648805/job/109618719716) 在 Testbox 监视器中等待 30 分钟，空闲设置为 30 分钟。不要将租赁百分位数视为活动命令百分位数，也不要为新策略声明测量的超时率。默认 60 分钟是操作选择；在设置 15 分钟闲置上限后重新测量，然后再将 30 分钟或 8 级设为一般默认值。

这些控件涵盖使用此存储库中更新的工作流程的调度。 OpenClaw 包装器从 `main` 中为 Testbox `run` 和 `warmup` 选择工作流程，覆盖配置的引用并拒绝显式的历史引用。它的源胶囊仍然重建正在测试的结帐。旧包装器、直接历史引用调度、其他存储库、备用工作流程和 Windows 检查工作流程位于共享池之外。组织范围内的并发性、每个代币的准入、SKU 限制和硬性支出停止都需要提供商进行控制。

### <a id="ci-runner-routing"></a> CI 跑步路线

当前的扩展包边界检查使用16级。冻结目标保留其历史 32 类运行器和编译器策略。

当设置输入为 `24.x` 时，托管 Node 24 设置遵循工作流程的现有 `NODE_VERSION` 引脚。这可以防止运行程序图像刷新默默地选择不同的补丁版本。显式兼容性版本保留其自己的选择，自托管设置保留其现有范围和工具链缓存策略。恢复的缓存密钥不是运行时证明：在比较运行器后端时记录所选的二进制文件和 `node -v`。

运行者的选择不取决于拉取请求作者。同一存储库 PR 使用配置的后端。当存储库变量不可用时，分叉首次尝试（包括首次贡献者）使用默认的 Blacksmith 路由；他们的 Node 规划器使用铁匠计时和相同的容量提升。分叉检查作业会保留逻辑 GitHub 条带布局，因为分叉无法安装调整一体化作业大小的可信缓存。运行器放置与布局和缓存权限是分开的。维护者接受了增加的铁匠支出。 Fork 重试路由至 GitHub- 托管运行器。当变量不可用时，存储库后端覆盖无法重新路由 fork 首次尝试。推送和手动调度不受影响。缓存信任是一个单独的、更严格的边界：精确的依赖关系恢复需要来自 `openclaw/openclaw` 的拉取请求，而普通的 CI 从不发布共享档案。独立的值得信赖的温暖者拥有出版物。

QA Smoke 仅将 8 类用于上游 `main` 推送和调度首次尝试的混合四部分计划，并具有明确的当前目标分类。完整的 24 场景配置文件和冷私有运行时构建在 7-GiB 内存上限下在两个可用 CPU 上传递，无需交换、跳过或 OOM 事件；峰值内存为 5.96 GiB。较旧的目标、其他配置文件、手动和发布运行以及重试将保留其现有位置。场景覆盖范围、工人限制、交错时间和截止日期均保持不变。观察部署后的实际工作持续时间和计费情况；仅靠较低的跑步率并不能节省成本。

该表列出了默认放置。在符合条件的混合首次尝试中，[托管预算](/ci/capacity#bounded-hybrid-hosted-offload)可以将`security-fast`和仅浏览器扩展E2E行移动到`ubuntu-24.04`；当可选入场关闭时，将应用默认的铁匠路线。

Control UI 单位行 （`checks-ui`） 保留在现有的铁匠 8 级上，进行规范的 hybrid/RunsOn 首次尝试，并具有现有的 20 分钟超时。可选的托管入场不会移动这些碎片。显式托管路由（包括重试和 `github` 覆盖）保留 35 分钟超时。覆盖范围、工作人员和每次测试的截止日期均保持不变。

基线棘轮和 Node 分片在预检后独立启动；最后一扇门仍然需要选定的棘轮才能通过。独立棘轮使用铁匠 4 级进行同一存储库混合首次尝试、自动主运行和承认的资格调度。 `check-plan` 在未设置、`blacksmith` 或 `hybrid` 后端（包括分叉 PR）的上游首次尝试中使用 16 类共享编译器快照内存。 GitHub 覆盖、重试、普通手动和冻结目标、RunsOn 规划器和其他存储库上下文保留托管规划。未设置或 `blacksmith` 后端的叉芯类型条带在当前自动首次尝试中也使用 16 级。它们的逻辑 GitHub 配置文件、五条带覆盖范围和仅恢复缓存权限保持不变；混合健康录取保留其现有的安置规则。编译器和 lint 行仍在等待其完整计划；合格的防护和依赖行在预检后启动。请参阅 [ 入场测量和成本 ](/ci/routing-costs#ratchet-admission-and-node-tests)。

当前上游核心 lint 条带在未设置、`blacksmith` 或 `hybrid` 后端（包括分叉 PR）的自动首次尝试中使用 16 类。相同的五个 fork 行仍然拥有其核心和扩展 lint 块；剩余的扩展块保留在组合的 `check-lint` 行中，该行已使用 16 类。独立的 `check-lint-extensions-*` 行仅限混合动力并保留其现有路线。 PR 缓存仅恢复。重试、普通调度、冻结目标、其他存储库和 `OPENCLAW_CI_RUNNER_BACKEND=github` 保留托管核心 lint；现有RunsOn及资格路线不变。

RunsOn 保留其独立棘轮和检查计划的托管位置，包括资格派遣。

同一存储库混合 PR 首先尝试使用现有串行编译器发现模式在托管 `ubuntu-24.04` 上运行 `check-plan`。完整快照对于该跑步者来说仍然太大。这会牺牲编译器执行时间，以避免在 type/lint 行开始之前进行第二次 Blacksmith 分配；主办策划者计入现有入场预算。分叉、其他后端、重试、push/schedule 和 manual/release 路由保留其现有的放置和发现设置。图形验证、选定的行和所有检查命令均保持不变。请参阅 [ 测量和鉴定 ](/ci/routing-costs#compiler-planning-queue)。

健康的合格主推和 Windows- 选定的 PR 可以额外卸载 [ 分配守卫 ](#hybrid-hosted-assignment-guard) 下的七个支票行。然后，仅 Main 就可以卸载 lint 和中央测试类型。每个决策都会消耗相同 45 行限制内的剩余容量；原来的跑步者仍然是后备。 Artifact 构建保留了 16 级：在预检和登机口开销之前，其托管最大值达到 898 秒。请参阅 [ 路由测量和资格差距](/ci/routing-costs)。

本机 Swift builds/tests、普通 CI iOS 构建阶段和外围扫描在 GitHub- 托管的 `xcode-27` 上使用 Xcode 27，预览 macOS 27 图像。此工具链更改保留了托管安置、职位数量、员工上限、覆盖范围和截止日期；它不添加铁匠注册。 Swift 源语言最低限度仍保持 6.3. 本机兼容性，完整的作业计时需要新映像上的证明。

iOS 屏幕截图碎片、商店发布及其仅屏幕截图操作在与可重用资格作业相同的预览图像上使用 `xcode-27-xlarge`。在 3-CPU、7 GB `xcode-27` 运行器上，iPad Pro 13 英寸模拟器耗尽了内存：`simctl` 和 XCTest 启动停滞了 60 到 100 秒，在启动或准备就绪时 iPad 捕获失败。屏幕截图使用没有 SimSlim 的库存模拟器。它为每种设备类型创建一个新的模拟器，然后在开始下一个之前关闭并删除它；仅屏幕截图作业接受选定的分支，而无需发布凭据。资格认证作业为其模拟器和隔离网关使用相同的较大运行器。库存资格使模拟器保持不变。在本机构建之后，每个手臂都会启动一个隔离的网关，并在启动新的模拟器之前通过 `device.pair.setupStatus` 准备其设置处理程序。状态调用会修剪过期的完成记录而不颁发凭证；应用程序使用的设置代码在启动后发出。同一个网关服务于实时配对、聊天和重新启动案例，然后在同一模拟器上的独立转录阅读器案例之前停止。这两个案件都必须在各自的期限内通过。

早期的托管路由验证使用 `macos-26`：重复的首次尝试导致 Blacksmith macOS 作业未分配，而其他 CI 作业已完成。在 [run 33616182173](https://github.com/openclaw/openclaw/actions/runs/33616182173) 中，托管重试在八秒内分配了所有三个等待的 Mac 作业； Debug/simulator 作业在 15 分 31 秒内完成。该历史结果早于 Xcode 27。完整的手动鉴定仍然需要完整的本地证据。

Node 测试规划器仅标记运行真实本机 grep 夹具的分片。当选定的运行程序映像未提供 `ripgrep` 包时，这些 Linux 作业会安装该包。其他 Node 分片不支付该设置成本。

依赖项预热器在设置后立即发布已完成的 pnpm 存储，以免相关的 SDK、构建或转换工作失败。所有启用缓存的 Node 设置都使用相同的工作区本地存储路径，包括仅存储读取器；操作在缓存兼容性中包含该路径。 Pnpm 的副作用缓存携带本机安装后输出，例如 Matrix 加密的二进制文件和版本标记，因此兼容的热安装会跳过下载。冷缓存和更改的本机构建输入仍然需要上游资产。当该存储对于作业工作区来说是私有的时，Linux 设置使用硬链接，包括托管运行器上的仅存储恢复。这可以避免在没有克隆支持的情况下在文件系统上复制缓存的包。共享或外部存储以及普通 macOS 安装保留其配置的导入方法； freeze-lockfile 协调和生命周期脚本仍然运行。安装程序在激活 pnpm 之前恢复配置的存储根。同一工件包含固定的 pnpm 包装器和 `toolchain/` 下的 Linux 本机可执行档案，由完整的 `packageManager` 引脚键入。 Bootstrap 在提取之前在私有暂存中检查其 SHA-512 哈希值；丢失或无效的档案会回退到运行程序映像，然后是注册表。精确的依赖关系存档包含相同的文件，并且依赖关系修复会保留它们。存储 v2 和精确依赖项 v4 条目重新种子一次以包含这些引导程序存档。缓存发布仍然属于每个后端上现有的温暖器。 Node 发现仅扫描工具缓存的可执行级别，在选择已安装的运行时之前避免捆绑 npm 依赖关系树。

在混合模式下，独立托管依赖项和代码预热作业填充 GitHub 的缓存后端。 Blacksmith 和 GitHub-hosted 缓存存档保持独立。有关完整的 Linux 和有界托管配置文件，请参阅 [ 缓存所有权和种子选择](/ci/scope-and-routing/node-test-lanes)。

### <a id="runner-backend-modes"></a> Runner 后端模式

`macos-swift` 通道构建一次 Swift 测试，并为每个作业运行一次每个测试。普通套件保留默认配置文件行为；渲染的快速聊天测试遵循新的默认配置文件进程，然后 AppState 隔离测试通过相同的资源拥有启动器在命名配置文件进程中运行。历史目标保留其原来的两个分区。每次启动都拥有一个私人住宅和一次性的、未锁定的默认钥匙串，直到测试进程组和输出管道关闭。 HOME和配置文件标记不隔离macOS服务；所有分区仅在一次性无凭证 macOS 工作线程上运行。当前支持启动器的目标将 Swift 测试并行性绑定到运行程序的逻辑 CPU 计数（上限为 12），用于自动运行、手动调度和重新运行尝试。只有早于资源所有者的冻结目标才使用串行回退。失败的测试会使作业失败，而无需在作业中重试。参见 [native 测试安全性 ](/platforms/mac/dev-setup#run-native-tests-safely)。

存储库变量 `OPENCLAW_CI_RUNNER_BACKEND` 控制 `ci.yml` 的运行器后端：

| 值                 | 灯道                                                                            | 重车道                                                                      | 重新运行行为                                                                        |
| --------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 未设置或 `blacksmith` | 铁匠优先，使用现有的手动调度和分叉后备                 | 铁匠优先，使用现有的手动调度和分叉后备           | 现有行为不变                                                        |
| `github`              | GitHub-托管                                                                          | GitHub-托管                                                                    | 每个可配置作业均保持托管状态                                                 |

Mac Node 覆盖范围在现有跑步者标签上使用两个不相交的包脚本部分。提升生命周期、技能和剩余运行时项目共享第一部分，以便其子流程消费者重用准备好的工作人员一代；原生工件、打包和检查工具共享第二个。所有 26 个文件都保持被选中一次。聚合 `test:macos:ci` 命令运行这两个部分；具有三个部分脚本的历史目标保留三项作业，而没有部分脚本的目标保留一项完整作业。项目执行保持串行，现有的两人、CPU-clamped 三箱 Mac 夹具和两箱结账限制保持不变。在每小时运行 38823827091 中，前两部分分配在测试中花费了 247 秒和 465 秒，对同一工作输入图分别进行了 64 秒和 90 秒的编译。将其运行时使用者分组会删除第二个编译并将其他运行时项目转移到较短的行。每个 Node 设置的相同运行花费了 137-140 秒，而之前的三行基线则花费了 68-118 秒；未更改的工具文件运行速度也较慢，因此总作业时间不是分区形状的受控比较。本地每小时计时确定了最终的挂墙时间。

OpenClawKit 软件包通道为其禁用 Talk 的构建和默认特征测试套件创建了一个新的暂存目录。 SwiftPM 在启用 Talk 时重新规划和重新编译特征相关模块，同时保留该作业中的依赖性解析和检查工作。没有从早期运行中复制任何产品。 no-ElevenLabs 选择退出防护和完整的默认特征套件均保留；清理在成功、失败、取消或未选择的套件后运行。在每小时运行 38817599758 中，第二个新图在编译前在 16.9 秒内重复了 19 次依赖操作。使用一次划痕的本地仅编译重放消除了这些重复操作，并验证了在启用 Talk 的情况下重新编译的所有三个生产模块。托管已用节省来自下一个自然小时。

恢复后，恢复切换到 GitHub 回退之前记录的值。例如，使用以下命令恢复之前的 `hybrid` 设置：

```bash
gh variable set OPENCLAW_CI_RUNNER_BACKEND --repo openclaw/openclaw --body hybrid
```

仅当先前未设置变量时才删除该变量；删除选择默认的Blacksmith-first路由：

```bash
gh variable delete OPENCLAW_CI_RUNNER_BACKEND --repo openclaw/openclaw
```

`ci.yml` 不会检查 Blacksmith 或改变此变量。混合回退针对每个作业，并且仅当协调器重新运行工作流或选定的失败作业时才激活。
