OpenClaw 的当前 GitHub 运行者注册存储桶报告 `gh api rate_limit` 中每 5 分钟有 10,000 个自托管运行者注册。在每次调整之前重新检查 `actions_runner_registration`，因为 GitHub 可以更改此存储桶。该限制由 `openclaw` 组织中的所有 Blacksmith 运行者注册共享，因此添加另一个 Blacksmith 安装不会添加新存储桶。

将铁匠标签视为爆发控制的稀缺资源。仅路由、通知、汇总、选择分片或运行短 CodeQL 扫描的作业应保留在 GitHub- 托管运行程序上，除非它们测量了 Blacksmith 的特定需求。任何新的 Blacksmith 矩阵、更大的 `max-parallel` 或高频工作流程都必须显示其最坏情况下的注册计数，并将组织级别目标保持在实时存储桶的约 60% 以下。对于当前的 10,000 个注册存储桶，这意味着 6,000 个注册操作目标，为并发存储库、重试和突发重叠留下了空间。

受保护的缓存预热器有两行平台：现有的 Linux 工作负载和一个托管的 macOS pnpm-store 发布者。它的每引用并发性和挂起运行合并保持不变。每一次承认的温暖运行都会增加一项托管 macOS 工作，并且没有铁匠注册； Pull-request CI 不添加作者或职位。在声称节省设置时间之前，本机生产者和消费者测量必须包括缓存传输、提取、安装和存档大小。

每个承认的上游主管道都在保留的 `docker-seed-e2e` 作业中选择已发布的升级绊线，该作业已包含在当前 5,110 注册到达信封中。仅文档的主要提示仍被 `**/*.md` 和 `docs/**` 推送过滤器排除。承认的主推保留相同的两个非取消奇偶校验槽；该边界包括两个活跃运行和两个合并后继运行。它并不假设每个推送的提交都会开始运行。每周更新迁移调度针对本机操作符状态的每个受支持基线使用一个目标 Docker 组，并对候选相关前身进行综合清理。如果该前身不在支持的集合内，它会添加一个现有的矩阵行：最多 5 个目标作业，加上图像准备、组规划器和混合参考验证器，每周运行最多 8 个 Blacksmith 注册。其单独的非取消并发组合并挂起的计划运行，并且无法取消手动验证。发布检查重用相同的有界分组和未更改的 32 个作业上限：在四个不同的基线上，正常的包验收选择 16 个目标作业（当前身需要自己的行时为 17 个），而发布浸泡选择 20 个。三场景组限制和 32 个作业并发上限保持不变。额外的每周突发和扩展发布作业共享现有的发布空间、相邻存储库和结转；在进一步更改扇出之前，仍必须检查实时共享存储桶。

每小时扩展运行时检查重用现有插件预发布所有者，其 `max-parallel: 12` 未更改。当前库存发出 8 个批处理行、18 个 Telegram 文件行以及 6 个没有包元数据和根扩展测试的插件文件行：每个承认的每小时运行最多 32 个 Blacksmith 注册，包括营业额。单个非取消计划时段可防止与另一个每小时延期运行重叠。允许活动运行完成并在五分钟的时间段内开始待定的替换，从而保留两个完整的库存，或 64 个注册。将这些添加到 5,110 自动运行信封中得到 5,174。完整的每小时 Node 库存有一个单独的 77 行上限，比不变的 70 行推送上限高出 7 个。预订所有 4 个主要到达站的这 7 排座位后，登记人数增加了 28 人，保守的数字为 5,202 人，低于 6,000 人的参考目标。这不会花费因删除正常 CI 的七个部分扩展行或不相关的 PR 扩展作业而节省的费用。 Manual/release 的入场仍然在该范围之外。在进一步增加之前重新计算库存并检查实时组织存储桶。

三个 Mac Node 部件在 `github` 和 `hybrid` 上每次运行都会添加两个托管作业，并且没有添加 Blacksmith 注册。正常的铁匠路线会在每次合格尝试中添加两次注册 - 1 次推送或 PR；手动运行和重试仍然托管。矩阵并发上限为 3。 GitHub 记录的 Enterprise macOS 并发限额为 50，与其他托管 Mac 工作流程共享；它不保证跑步者立即入场。此拆分不会改变运行器类别或存储库容量设置。

`Release npm Cache Warm` （`release-npm-cache-warm.yml`） 在计划和手动触发器上运行托管 Linux 作业，以从最新发布的 OpenClaw 包中准备 npm 下载种子，并禁用生命周期脚本。它的并发组与推送触发的 Vitest 预热是分开的，因此较新的推送无法取消待处理的种子。计划从 `main` 运行发布，因此新的发布分支可以通过 GitHub 的默认分支缓存范围恢复该种子。每个种子开始时都是空的，并且只包含当前的基线依赖图。跨 OS 发布检查首先恢复其候选特定缓存，然后恢复匹配的 runtime/suite 缓存，然后恢复此共享种子。仅归档npm的内容寻址`_cacache`目录；安装前缀、OpenClaw 状态、npm 日志和可执行 `npx` 缓存保持最新状态。生产者和消费者使用相同的相对归档路径并启用跨OS归档。 npm 保留正常的新鲜度和完整性检查，并下载缺失的特定于平台的软件包。这会为每个计划或手动预热运行添加一个托管的 Linux 作业，没有推送作业，也没有铁匠注册。

上游 PR 使用有界变更所有者 Node 计划，包括受保护的传递消费者和固定冒烟测试。广泛的投入保留了其所有者的覆盖范围；丢失或未解决的选择会导致预检失败。上游推送使用集成紧凑型。本机紧凑配置文件的上限为 90 行，GitHub-hosted 的上限为 96 行，插件后备打包的上限为 50 行。最终标准 Node 矩阵还强制执行 70 行推送、77 行主层验证行或 130 行 PR 行，包括精确计划。缺少更改的路径、缺少当前规划器功能和规划器错误会导致预检失败，而不是发出不完整的成功矩阵。批准的历史调度保留其完整的命名计划。计算每个发出的矩阵行和非矩阵作业，包括保守的六行 Android 库存，与并发无关。

Android保留4个普通排和6个全手动排。上游推送和 PR 在 Blacksmith 上的首次尝试重叠了所有四行，包括分叉 PR。 GitHub 覆盖、重试、手动调度、调度和其他存储库保留两个。 Fork 的第一次尝试已经使用了 Blacksmith；并发上限遵循该路线，而不需要相同的存储库头。前两排叉帽在 10 月 1 日的四次运行（36941929665、36941497583、36939940862 和 36941476576）中添加了第二个大约十分钟的波浪，产生了 20.7–22.5-minute 总数。四路入场消除了强加的等待，而不会改变作业数量或计划的跑步时间；自然跑步必须确定实际的跑墙时间。将 app lint 重新分配给现有的 Wear 和 Kotlin-lint 行不会添加任何作业或注册。三行上限使每个作业低于 10 分钟，但在 [run 35812544118](https://github.com/openclaw/openclaw/actions/runs/35812544118) 中留下了 941 秒的 Android 跨度，因此正常运行允许所有四个独立行一起运行。保守的六排配额和 `4 × 150 + 21 × 210 = 5,010` 注册范围保持不变，低于 2026 年 9 月 23 日检查的 10,000 个实时桶的 6,000 个运营目标。此配额并不能确定实际跑步者的可用性或测量的挂墙时间改进。

在打包紧凑的核心工作之前，Preflight 保留实际附加的插件 Node 行。因此，当超出剩余的 Node 预算时，甚至低于独立压缩上限（90 个本机行或 96 个托管行），托管工具尾部压缩就会开始。 Dist描述符属于它们单独的矩阵，不消耗这个Node预算；它们仍然计入紧凑型上限。现有的文件所有者分割、时间权重、流程边界、运行者要求和准入限制仍然具有权威性。如果压缩无法容纳完整的库存，预检将失败，而不是放弃工作或增加任一上限。

批准的行上限增加将紧凑计划从 80 行增加到 90 行，最终 Node 矩阵从 64/120 行增加到 70/130 push/PR 行。它为测量的隔离网关服务器系列和测量的插件信封包装预留了空间。在限制下，每次运行可以在推送上允许另外六个 Node 注册，或者在 PR 上允许另外十个注册；紧凑行已包含在该总数中。在保留的 4 个 main/21-PR 到货范围内，增量为 `4 × 6 + 21 × 10 = 234`，将保守上限从 4,776 增加到 5,010。运行器类、工作线程、矩阵并发和超时保留其现有策略。仅增加上限并不能改善运行时间。

完整的手动 Node 计划将 Gateway isolated/database-worker 队列与现有的 64 个文件信封限制和固定文件权重分开。在完成 18 个独立文件并传递 235 个数据库工作文件中仅 137 个的案例后，运行 35727279415 耗尽了其 60 分钟的作业。当前的 257 个文件库存现在占据了五个完整的、不相交的条带，增加了四个手动作业，同时保留了配置、两个工作人员和作业截止日期。调度将这些行路由到 GitHub- 托管的跑步者，因此拆分不会添加铁匠注册。最终的 70/130 push/PR 行上限不变；文件限制和建议权重都不能保证有效时间。

共享插件包、QA 和提供程序套件使用本机 Vitest 分片，其大小根据现有的 90 个文件信封预算确定。他们的完整配置仍然拥有发现和排除；盘点库存永远不会将执行范围缩小到直接更改的插件。在 `2f7fb353`，Catch-all 在 6 个作业中有 486 个计数条目和 474 个有效文件，QA 在 3 个作业中有 238/232 个，而提供商在 4 个作业中有 275/256 个。统计条目包括 Vitest 排除的文件，因此预算比较保守。每个作业保留其现有的工作限制、隔离策略和每个文件模块清理。

进程限制插件回退使用每个测试文件的有效配置所有者，包括从普通插件套件迁移到数据库工作人员的文件。广泛的后备保留了完整的选定配置清单，包括没有包清单的内置插件；仅插件的更改保持其范围。即使是单个有界信封也会保留其显式文件范围，因此它无法静默执行更大的整个配置。不均匀的有界块使用自己的文件计数和现有的成本率；原生 Vitest 分片保留完整配置估计的同等份额。

路由到数据库工作人员配置的所有文件共享 20 个文件 CI 作业上限，包括每个共同定位的信封。有效配置具有分类；迁移的文件还保留任何更严格的原始插件作业和进程限制。这会将 [run 35176277297](https://github.com/openclaw/openclaw/actions/runs/35176277297) 中的 185 个文件本机信封划分为 10 个不重叠的信封。在工作截止日期之前，该运行持续通过测试超过 58 分钟；这是一个下限，而不是完整的家庭计时样本。在 [run 35477485803](https://github.com/openclaw/openclaw/actions/runs/35477485803) 中，仅根计数允许在一项串行作业中包含 149 个数据库工作文件；其测试步骤耗时 27 分 30 秒。现在，上限可以防止超大尺寸的迁移信封及其在成本包装期间的重新组装。分叉隔离、进程文件限制、工作人员限制、超时和 50 个作业后备上限保持不变。成本估算仍然是建议性的；托管 CI 必须确定最终的作业持续时间。

普通的 Codex 测试使用隔离的线程工作线程并从共享工作线程预算继承文件并行性。每个文件都会退役其模拟模块图和全局变量；一个普通的进程最多包含24个文件。数据库工作线程路由的 Codex 测试已经使用隔离的分叉并保留独立的 12 个文件绑定。 300 秒无输出看门狗、测试截止时间和断言保持不变。这些调度界限与时间权重校准无关；更大的流程界限本身并不能建立壁时间或矩阵行的改进。

精确和后备插件信封共享相同的打包所有者和每个作业 300 秒的总计估计预算，包括相同配置的多个信封。该预算仅适用于变更扩展的工作；紧凑核心预算没有变化。成员保留兼容的 runner/dist 要求并一次运行一个。打包保留每个生成的信封的子进程、环境、本机分片参数和包含范围，包括进程限制的 Codex、Matrix 和 Telegram 工作。具有相同准备要求的信封在其单独的流程运行之前共享一个构建；其费用一次收取。不同的准备模式保持独立，超出预算的信封保持单独。工作线程限制、运行程序类别、超时、覆盖范围和串行故障停止行为均保持不变。

在 9 月 22 日盘点库存时，将入场预算从 240 秒增加到 300 秒，将同样的 119 个信封打包到 40 个而不是 47 个工作中。他们的预计总工作时间仍为 10,140 秒。减少 7 个 checkouts/setups 预计可节省 315-420 机器秒，每个作业节省 45-60 秒。这是包装预测，不是测量经过时间的证明；请参阅 [ 路由成本和 15 分钟资格 ](/ci/routing-costs)。所有四个行上限保持不变。

对于显式限制的插件配置，先决条件所有者标识需要构建运行时的文件。当这些文件跨越多个信封时，生产者会在应用现有文件限制之前对它们进行分组，因此不相关的测试不会导致重复的运行时构建。每个生成的信封保留其实际的先决条件费用和测量的文件成本。整体配置的原生 Vitest 分片保留其完整的发现和准备合同。

### <a id="fixed-job-preparation"></a> 固定作业准备

9 月 20 日的开销样本测量了绿色主运行 `35520044205` 和绿色 PR 运行 `35456568835` 中的所有作业步骤。 Main 有 72 个活跃作业和一个 16 分 45 秒的工作流程墙； PR 有 152 个活跃作业和 26 米 25 秒的墙。结帐中位数为 9/8 秒，Node 设置中位数为 13/13 秒。在每次运行中，结帐和设置消耗了 30.63/82.18 机器分钟。作业 API 将复合设置报告为一步；采样日志确认了 dependency/store 命中，并在测试步骤内以 7.1–21.7 秒的时间测量了冷工准备情况。这些不同的清单是基线，而不是配对的性能比较。

编译工作人员重用不会添加任何作业、注册、测试流程或工作人员。它使用现有的受保护的温暖和仅恢复操作缓存机制。温暖的结果必须包括传输、验证和联合清理；仅靠存档命中并不能节省成本。初始 PR 运行保持冷状态，直到受保护的预热器发布新的命名空间。删除未使用的构建存档上传可节省 5-6 秒的时间，加上工件作业中的打包和插件资产上传时间，这不是任一基线中的完成瓶颈。 Node 运行时构建保持独立，以保留并行启动和私有 QA 输出变体。 Checkout 已获取深度一选定源；历史测试先决条件和修订比较输入保留其现有所有者。

对四个 CPU、15.4、GiB、RAM 和 Node 24.19.0 进行 Linux 测试箱检查，测量准备情况并在 8.43/9.44 秒内进行联合清理，无需重复使用和恢复 30 MiB 存档后的 3.21/3.17 秒。峰值进程RSS从2.59–2.66 GiB下降到0.55 GiB。两个样本中点在下载和提取之前节省了 5.75 秒；运输成本必须低于改善消费者墙的成本。生产者在冷缓存上花费了 9.38 秒。这些是准备测量，而不是完整的工作流程或生产缓存命中率。

| 4 / 8                      | 2 / 7.66 GiB        |                                2 |                         2 |
| 16                         | 4 / 15.42 GiB       |                                3 |                         2 |
| 32                         | 8 / 30.95 GiB       |                                8 |                         2 |

组别针可以降低这些上限。 `agentic-gateway-core-2`、`agentic-agents-embedded-base-*`、`agentic-agents-embedded-run` 和 `agentic-agents-tools` 系列、命令组和整个 `agentic-cli` 组使用在 Blacksmith 和混合配置文件上测量的工人，以及 `fallbackMaxWorkers: 2`。完整的 CLI bin 在打包后请求 `blacksmith-32vcpu-ubuntu-2404` 并保留串行执行。观察到的八-CPU/30.95-GiB分配可以接纳八名工人；实际CPU，内存和负载仍然决定上限。分片运行程序在托管、冻结、约束或重叠执行上应用两个工作人员后备，与任何较低的作业或组限制相交。即使工作流程上限为 3，4-CPU/15.42-GiB 16 类分配也会收到该回退。 GitHub-托管规划、`agentic-cli-process`和其他时序敏感组保留其现有引脚。网关计划仍然独家运行；未经证实的兄弟姐妹共享其序列号保留其两人工作组上限。 CLI 库存、拆分策略、时间权重和准入预算保持不变。

`agentic-gateway-server-isolated` 系列（包括其数据库工作人员配置）使两名工作人员保持在 Blacksmith 和混合配置文件上。当前源首次登录 CI 超出了 8 名工人分配下不变的 90 秒截止日期；八名工人的基线控制在 85.4 秒内完成，几乎没有留下余地。两名工作人员预算恢复了冷启动空间，而无需更改测试截止日期、断言、库存或清理。现有的主机准入和回退规则、独立规划的 GitHub 配置文件以及单独的四工作网关方法策略保持不变。

`config/ci-test-timings.json` 记录 UI 和网关 E2E 文件、PR 工具文件和紧凑型 Node 组的 CI 测量值。 UI 和紧凑型包装商更喜欢主动重量而不是其内部冷启动表。 UI E2E 密钥是存储库相对路径，包括 `ui/src/pages/` 下的测试，每个文件估计包括测量的分叉、导入和设置开销。紧凑组有单独的 Blacksmith 和 GitHub-hosted 测量，从作业 API 跑步者标签中选择（`blacksmith-*` 与托管 `ubuntu-24.04`）；混合和大组条带调整继续使用其现有策略。紧凑权重使用完整的 `[shard:x] begin` 到 `end` 范围，保留进程启动和测量运行中的任何争用。普通铁匠紧凑型工作可以同时执行两组；串行作业保留 `planConcurrency: 1`。改装保留了每个完整的子跨度，包括争用，而不减去设置或重写历史成本。跑步者资料校准仍然是一项单独的准入政策。

本机 32 类上的纯源单例还可以在分片重命名和重新分区时保留稳定的计时标识。此配置文件需要八个实际 CPU、28–32 GiB RAM、八个工作人员上限、一个承认的外部计划以及已确认的当前自托管运行。确切的配置、文件和支持的环境可识别测量。仍需要两次独立的成功观察。只有最后的串行单行才使用这个价格；打包、共享行、托管执行和后备工作线程策略保持现有的估计。这些完整的子跨度已经包括进程开销。

对于拆分紧凑组，改装还记录一次运行和跑步者配置文件中完整一代的父成本。它将每个部分的中值跨度相加，采用该运行中最大的完整代或直接亲代测量值，并应用相同的两次运行最小值和中值规则。稳定的父估计在文件添加和重新分区后仍然存在，而精确的子键继续仅描述其原始清单。部分世代不能创建或降低父估计；观察子级可以在修剪过程中保留现有的父级。来自不同运行、配置文件或代的零件永远不会形成一个整体。

网关 E2E 使用与 UI E2E 相同的贪婪分区所有者。测量的文件持续时间包括套件挂钩；新文件使用按已发现文件的每字节测量秒数缩放的源字节。如果没有测量，网关分区将单独使用源字节。 CLI JSON 套件按命令系列划分，因此其现有案例可以跨四个分片运行，而无需不可分割的串行尾部。

紧凑的计划是在飞行前一次构建的。 E2E 分片独立构建其分区，因此它们必须从结账中读取相同的已提交文件。他们从不下载计时工件或查阅恢复的计时缓存。丢失或无效的定时文件，或`OPENCLAW_CI_TEST_TIMINGS=0`，使用整个文件的冷启动估计；过时的密钥无法更改已发现的测试清单。

使用经过身份验证的 `gh` CLI，运行 `pnpm ci:timings:refit` 以重新生成文件。每次调用都会提前 7 天冻结一个 UTC 上限和下限。每个运行列表页面都使用这两个边界。在该窗口之外返回的运行创建时间戳无法验证。在下载运行日志之前，收集器会验证所有捕获的尝试的作业元数据。成功的作业如果缺少完成、来源无效、启动时间过长、时间顺序颠倒或在元数据观察时间之后完成，仍然无法通过验证。

在窗口内创建的运行可以在其冻结上限之后完成，同时收集早期队列。当其他有效的成功作业在该截止之后结束时，计划采样会跳过整个运行，报告其 ID 和截止，并在不消耗样本配额的情况下寻求替代。它永远不会下载该队列的日志，也不会仅将较晚的作业放入明显完整的库存中。显式 `--tooling-run` 请求会因运行 ID 和中断而失败；两条路径都不会移动窗口。

改装寻求在 `main` 上运行最多五个已完成的计划 `ci.yml`，并得出成功或失败的结论，并从成功的作业中解析紧凑的测量结果。即使每次推送测试工作被禁用，计划的 CI 也拥有主要验证，因此跳过的推送运行无法隐藏其测量结果。当测试文件与采样的主版本不同时，UI 文件样本将被排除。这些文件保留其现有价格，直到匹配源样本满足正常的独立运行和替换频段规则。排除的样本永远不会提供修剪更改文件的价格的证据。共享助手或产品更改仍然会影响未更改的测试；这些权重仍然是建议性的。取消、超时、中立和其他工作流结果被排除在外。仅文档运行和不可解析的日志不会填充该配额。失败的工作流程仅提供正时序样本：它们丢失的作业永远不会被视为修剪缺失键的证据。成功的工作流队列保留其现有的修剪策略，包括与失败的工作流样本混合时。它还寻求最新的五个成功的 `ci.yml` `pull_request` 运行，并提供紧凑或编号的工具测量，跳过仅文档和不可解析的队列。收集器可识别普通、`changed-compact` 和 `changed-config-compact` 作业，并为两个计时系列读取每个日志一次。这些测试执行 PR merge-ref； `source` 记录该来源与上游主运行和发布运行分开。 PR 计划可能会选择一个子集，因此它们的测量永远不会修剪未观察到的紧凑、运行时或工具权重。 PR 紧凑样本仅更新精确选择器子键：选定的子集可以共享缩减的完整库存的父级名称，因此其子级和不合格的直接跨度都无法对该父级重新定价。 Main 的直接采样和完整生成折叠保持不变。紧凑样本保留其发出的库存密钥和流道配置文件。当历史密钥具有不同或不明确的工人上限时，改装将保留其之前的价格，而不是像政策那样进行平均，包括折叠的母公司成本。它使用执行器的最低规则与声明的作业和组工作人员限制相交，并根据执行器记录的 CPU、内存、计划准入、运行程序环境和冻结目标事实解析声明的后备限制。未知的后备入场保留之前的价格。可靠的继承限制也成为运行时放置标识的一部分。这些上限描述了公认的限制，而不是动态内存压力下的实际工作人员。即使每个观察到的运行都使用相同的后备，与显式 `#workers-N` 或 `#file-parallel-N` 计时标识冲突的公认上限也无法取代该标识的价格。当前工具文件测量在规划器中处于活动状态。更新的 9 月 26 日队列、有界串行包装和普通容量重用适合现有的行上限，而无需激活运行 `35506602947` 的旧上限计划。该地图保留了单独的 Blacksmith 和 GitHub 测量值。当文件移动时，编号的工具父项及其子项计时键会发生变化，因此每个文件的成本可以在重新打包后继续存在。直接轮廓测量不按比例缩放；托管回退使用测量的 Blacksmith 文件和现有托管因素。未测量的文件使用剩余的冷提示或正的两秒默认值。

这些样本早于 17：33 UTC 转轮容量恢复。它们保留了旧分配的争用，因此这些预测不是测量的加速。验证 PR 和第一次主运行上恢复的八个 CPU/two-child 准入、最长紧凑作业、总挂起时间和发出的注册计数。

少于两个独立的主要契约贡献者会导致调用失败。如果紧凑键和运行时放置观察都不满足现有的独立运行采样规则，它也会失败。保留的基线重量和释放测量不能满足这些检查。两次失败都会使定时文件保持不变。测量仅来自成功的 UI E2E、网关 E2E 和紧凑作业；紧凑组还需要 `exit 0` 标记。每个参赛作品至少需要两次运行样本；一次运行中的多次尝试仍然只为每个密钥和配置文件贡献一个样本。仅当该配置文件在至少三个采样的成功工作流程中的每一个中至少有一个观察结果时，并且仅当每次贡献运行（包括失败的工作流程）中都不存在该键时，才会对键进行修剪。库存不完整的重复运行片段不能通过更改其顺序来成为修剪证据。完整库存贡献运行较少的配置文件保留所有以前的密钥；丢失或无法解析的日志不计入阈值。空运行和 PR 变更表中的删除仍然很明确。在取中位数之前，高于 2.5 倍密钥中位数的样本将被丢弃，并且当新中位数在 15% 以内时，现有权重保持不变。 UI E2E 开销是中值分片 `(wall - body) / fileCount`，限制为 0–5 秒。

空的 `compactGroupSeconds.github` 地图被设计为冷启动行为：主要紧凑作业通常在 Blacksmith 上运行，因此托管配置文件将保持其源内 `COMPACT_GITHUB_GROUP_SECONDS_HINTS` 回退，直到托管观测值满足采样最小值。稍后在混合后端上的主要尝试，或者使用 `OPENCLAW_CI_RUNNER_BACKEND=github` 的主要运行，可以自然地填补它。一旦记录，托管权重将在所有 Blacksmith 窗口中幸存：修剪需要从采样窗口中至少三个托管运行进行观察。成功的 PR 紧凑样品保留其精确的执行身份，并且永远不会建立库存完整性或将选定的子集折叠到不合格的系列重量中。

`CI Test Timings Refit` 工作流程每天 09：43 UTC 运行，并支持在 `main` 上进行手动调度。当权重发生变化时，它会使用有限的采样运行 ID 和完整报告工件的链接更新单个 `ci/test-timings-refit` 分支和 PR，并保留 30 天。完整的更改条目表保留在该文件中，而不是步骤输出或发布者的环境中；无效或过大的 run-ID 摘要在不截断报告的情况下无法发布。它永远不会推送到 `main`；未更改的权重不会产生提交或 PR 更新。 gitignored `.artifacts/vitest-shard-timings.json` 仍然是本地测试项目运行程序的单独整体配置定时缓存，而不是这些 CI 打包程序的输入。

共享的 generated-PR 发布者在其租用分支推送之前刷新 `main` 并拒绝过时的生成器输入或重叠的定时文件更改。它使用单独的存储库范围的 GitHub 应用程序令牌进行分支和 PR 写入；工作流程的 `GITHUB_TOKEN` 仅具有内容读取权限。应用程序创建的事件会触发 CI，而无需 `GITHUB_TOKEN`- 特定的工作流审批步骤。正常的存储库审查和必要的检查仍然适用；此工作流程不启用自动合并。请参阅 [GitHub 的工作流程触发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#triggering-a-workflow-from-a-workflow)。

## <a id="bounded-hybrid-hosted-offload"></a> Bounded 混合托管卸载

自动上游混合首次尝试在添加短作业之前对完整选定的托管库存进行计数：控制和缓存作业、每个选定的检查或 Node 矩阵行、文档和 i18n、性能和托管本机作业。预检记录 `hybrid_hosted_base_rows`、`hybrid_hosted_total_rows` 和 `hybrid_hosted_offload`；工作流防护独立扩展实际作业门、矩阵和运行器表达式以验证计数。普通的同一存储库混合预检和门，加上选定的 PR 故障报告器，是强制基础托管行；它们在允许可选卸载之前消耗空间。 Fork、qualification 和 RunsOn 控件保留自己的记账和路由。性能行使用其现有的 `run_control_ui_performance` 所有者；未引入 40/45 行限制、作业或并发增加。

`HYBRID_HOSTED_BASE_ROW_LIMIT` 为 40，`HYBRID_HOSTED_ROW_LIMIT` 为 45。在 40 个基本托管行或低于 40 个时，预检可能会将 `security-fast` 和浏览器扩展 E2E 行移动到托管 Ubuntu，通过此准入最多添加两行且永远不会超过 45。超过 40 个基地托管行，都保留了现有的铁匠路线。无论是否可选托管入场，三个 `checks-ui` 单位碎片仍保留在现有铁匠池中；他们的测试、工人和铁匠超时都没有改变。超过 45 的符合条件的基数会发出行数警告并保留完整的基数清单。 45 行预算限制可选卸载准入；它不会拒绝现有覆盖范围或重塑不合格的后备清单：重试、手动和冻结目标、其他存储库和 `github` 中断覆盖保留其现有路由，包括已经超过 45 行的完全托管运行。

在此许可之后，上游主推送和受信任的 Windows- 选择的 PR（具有完整紧凑的 Node 计划和一个串行行中至少 500 预测秒）可以将七个检查行移动到托管 Ubuntu：依赖项、五个核心测试类型条带和运行时拓扑架构。扩展包边界保留 Blacksmith。他们之前的托管行保留保留在准入中，因此其他检查保持相同的阈值；报告的托管总数仅计算实际卸载量。这五个条带分布了相同的完整编译器图，以前分为两行和中央类型检查作业。单独的 `hybrid_hosted_checks` 决策需要新鲜、健康的 [ 分配证据 ](/ci/runners#hybrid-hosted-assignment-guard) 以及在同一 45 行限制内为每个选定的检查提供足够的空间。没有测量到的延迟下限的精确 PR 将保留其现有路由。

当前的 6 个混合扩展 lint 条带是基础托管清单的一部分。当托管入场不可用时，类型拆分最多添加三个铁匠注册；使用现有保守的四 main/21-PR 到达信封，153/213 注册范围变为 156/216，即 5,160 个注册，低于 6,000 个操作目标。无 Node 矩阵上限或托管准入限制更改。为每次运行保守地保留额外的真实网关行会将信封提高到 157/217，即 5,185 个注册 （`4 × 157 + 21 × 217`），使 815 个低于操作目标。此保留不花费普通 PR 现有的证明层遗漏；符合条件的混合托管库存保持不变，因为这些行保留了 Blacksmith。

主推则考虑 `hybrid_hosted_main_checks` 下的 lint 和中心测试类型；神器构建保留铁匠。此准入仅消耗剩余的托管容量，并且需要较早的检查准入。公共关系保留铁匠来担任这两项核心工作。完整的工作流程目标为十五分钟，包括分配和设置；将精确的头部计时与该目标进行比较。超时保持不变。

Control UI E2E 分片、QA Smoke、真实网关检查和 Android 保留其现有路由。测试库存和工人限制保持不变。安全性会等待预检的原始预算决策，并且在预检失败后仍会运行，除非工作流程被取消。托管分配延迟和普通缓存设置可以抵消计算节省，因此在扩大准入之前比较第一次精确头运行的 hosted/Blacksmith 行计数和队列时间。
