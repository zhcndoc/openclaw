## <a id="routing-from-measured-wall-time"></a> 根据测量的墙壁时间进行路由

使用 GitHub-hosted 运行程序进行适合工作流程剩余时间的独立检查。在测量的工作尾部威胁完成的地方保留铁匠。在为其分配生产层之前，按工作负载验证 RunsOn。在容量检查中请求铁匠8/16/32个标签交付2/4/8个CPU；标签不是工人计数。

当前的包边界检查要求附加检查矩阵和共享 SDK 生产者中的 Blacksmith 16 级。冻结目标保留32级。现有的两个 CPU 保留允许两个编译器执行观察到的四个 CPU 16 类分配，而四个编译器执行八个 CPU 32 类分配。编译器、金丝雀、托管、重试、信任和缓存策略保持不变；这不会增加任何工作或注册。附加检查行有 40 分钟的截止时间； SDK 制作人保留自己的预算。

10 月 13 日的规模审查涵盖了过去 24 小时内的 2,063 个边界作业。在 32 个班级中，中位数和 p95 峰值内存分别为大约 31 个 GiB 的 26.35% 和 27.66%，没有报告 OOM。中位数和 p95 工作持续时间分别为 183 秒和 292 秒。这些测量结果支持较小的跑步者获得资格；他们不衡量其运行时间或节省的费用。

16 级 （`36248684656`） 的历史完整库存运行时间为 569 秒，32 级 （`36269840991`） 的历史完整库存运行时间为 301 秒。编译器优化在这些运行之间也发生了变化，因此它们不会隔离运行器的效果。在声称成本降低之前，先比较等效的工作负载和缓存状态：只有当运行时间增长不到两倍时，将运行速度减半才能节省资金。

精确的插件信封和未分割的两个工作人员命令信封现在使用配置、完整的文件清单和工作人员绑定的身份来提供现有的计时所有者。插件行序号从不识别工作负载。静态插件费率仍然是未衡量选择的后备方案，改装商在更换价格之前仍然需要两次独立运行。保守的单运行楼层在承诺的计时来源中明确标记。超过 300 秒的精确测量的多文件核心子级可以再次拆分，而无需重新定价其兄弟级或将不同的容量样本合并到父级中。单个文件溢出仍然可见。

网关方法更喜欢测量当前范围和工作线程策略，然后是该策略的完全所有者。在这些存在之前，匹配的老年工人范围和完整所有者测量仍然是准入楼层。更改两个关键限定符不得丢弃现有的所有者测量。

受进程限制的插件所有者还可以在信封更改期间保留每个文件的调用价格。这些价格与整个围墙的价格有着明显的区别；共享包装器开销只收取一次。只有每个流程都成功完成一系列收据并声明一份文件才符合资格。其他流程所有者和缺失的测量保持其现有的估计。

### <a id="telegram-process-overlap"></a> Telegram 过程重叠

具有至少两个单例进程的纯源 Telegram 数据库工作线程信封可以与当前自托管 Linux 运行器上的两个内部进程重叠。准入需要一个明确的当前目标（`FROZEN_TARGET=false`）、来自共享运行时选择器（包括 `bun-compatible`）的一个未更改的 Node 调用、两个工作线程、一个外部计划、调度程序拥有的缓存、至少两个实际 CPU 以及 7.5 GiB 有效内存。有效内存是物理内存和正有限进程约束中较小的一个。其他选择或容量不足保留一个内部流程。每个测试文件都保留自己的流程，并且焦点CI在失败后仍然停止承认新工作，同时加入承认的同行。

执行器报告实际的内部并发性，包括串行回退。它的值参与现有的受环境限制的计时标识。平行收据仅提供完整的信封墙；重叠的文件持续时间永远不会被求和并减去以得出包装器开销。在该确切策略具有合格的测量结果之前，布局将保留保守的序列估计。

199 个案例包络在 Linux 测试盒（仅限于两个 CPU 和 7.65 GiB）上使用两个进程连续测量 184.40 秒和 147.31 秒。另外三场资格重赛耗时 147.46、146.13 和 149.34 秒。峰值聚合内存保持在 4.51 GiB 以下，没有 OOM 事件且情况相同。全行预算仍然需要来自自然发生的 CI 运行的资格。

存储平衡还使用了 36 个配置范围的模块工作提示，这些提示来自精确测试的合并的未更改的两个工作人员重放。设置、收集和套件经过时间指南放置；最长的文件永远不会除以工作人员数量。单独的 20 秒津贴涵盖每个子项一次的编译器和包装器工作。这些保守的四 CPU 测试盒提示不是八 CPU 原生 CI 文件墙。现有的整体观察仍然具有权威性，未知文件保留先前的估计，工人政策保持不变。大量存储的孩子在分裂时保留其测量的 32 类分配；孤立并不意味着跑步者较小。

## <a id="hosted-assignment-on-the-critical-path"></a> 关键路径上的托管分配

`openclaw/openclaw` 及其同一存储库 PR 中的普通推送和计划运行现在以混合模式将 `preflight`、选定的 `pr-failure-report` 和 `openclaw/ci-gate` 路由到托管 `ubuntu-24.04`。 Fork 的第一次尝试保留了铁匠的飞行前和登机口，他们的记者已经接待了。所有调度 qualification/release 覆盖、运行组、重试和其他后端模式都保留其现有路线。这将消除每个符合条件的 PR 的三个铁匠分配和每个符合条件的主运行的两个铁匠分配。在可选卸载之前，强制托管控件计数在现有 40 行基本阈值和 45 行准入限制内；没有新的工作或更高的限制。

10 月 15 日进行的 26 次 PR 运行样本记录了 148 分钟的飞行前等待时间，即每次运行平均 5.69 分钟、p75 12.9 分钟和最大 24.3 分钟； 26 人中有 8 人等了超过五分钟。 PR 墙上时间中位数为 35.6 分钟，而预检执行大约需要一到两分钟。一个单独的尾部对照样本等待了 27 分钟，完成了 12 秒的工作。这些观察结果确定了队列暴露；它们不测量托管路由更改的结果。

预计托管成本为每个同一存储库 PR 三到四分钟的标称舍入运行时间，三个控件的计算时间大约为两到三分钟。这是估计值，不是观察到的计费或已证明的工作流程加速。托管队列也可以延迟完成；在要求避免排队或减少工作流程占用时间之前测量第一次自然运行。繁重的作业、可选的卸载准入和所有验证命令保持不变。

这些 9 月份的观察结果之前激励了 16 级的包装核心棉绒行和 4 级的门。 Core lint 保留了其测量的铁匠路线。目前普通的同存储库混合控件使用的是上面的托管路由； fork、dispatch 和 RunsOn 覆盖仍然存在。逻辑 li​​nt 分区、单个 lint 线程、扩展 lint 行、主奇偶校验槽、工作流依赖项和截止时间均保持不变。 RunsOn 的 cron 证据不符合 RunsOn 放置的 lint 或门。在观察到的托管等待达到六十秒后，现有的健康所有者还会拒绝可选的检查卸载，取代了以前的三分钟阈值。当分配消耗其执行裕度时，这可以保护中心类型和依赖行，而无需更改 API 截止日期或测试覆盖范围。第一个本地候选者对两个 lint 行都使用了 8 类。其 PR 运行 `35813098351` 在 785 秒内通过，但核心 lint 1 花了 621 秒（lint 本身为 568 秒），而托管基线为 398 秒（lint 为 350 秒）。 Core lint 2 花费了 353 秒，而托管则花费了 323 秒。该修订版仅为较重的行保留了四个实际 CPU，以避免将队列节省花费在较慢的执行上。按照历史列表费率和旧托管运行时间保持不变，16/8 拆分的成本约为 $0.2984，而不是两个 8 级行的 $0.1923。这些未经四舍五入的估计不包括最低计费和辅助费用；最终的成本和墙壁比较由本地测量而不是预测决定。

第二个打包行随后在运行 `36422187813` 中耗尽了 15 分钟的限制。受控的 4-CPU、16-GiB 上限租约在 137.37 秒内使用现有的较大运行者 Go 策略完成了其未更改的条带 3、4 和 5。现在两排都要求 16 级。此次促销活动不会增加职位或注册；在完整的 15 分钟期限内，第二行与 8 类相比最多增加 120 类 vCPU 分钟。租用测量不是本机 CI 计时结果。

修改后的 PR 运行 `35814962786` 在 16 级上测量核心 lint 1 在 275 秒，在 8 级上测量核心 lint 2 在 385 秒。较重行的参考计算约为 $0.1467，而其 551 秒 8 级主形观测的参考计算为 $0.1469，以及较早的 621 秒 PR 观测的参考计算为 $0.1656。这些是不同 CI 环境中的未舍入的完整作业成本，不包括最低计费和辅助费用。修改后的工作流程仍然未能通过 UI 测试，并且托管平均等待时间为 118 秒；这不是一个完整的十五分钟资格赛。

此更改在普通混合主和同一存储库 PR 上添加了三个实际的 Blacksmith 注册。分叉 PR 保留逻辑 GitHub 检查配置文件，该配置文件发出 5 个 core-lint 行，因此它们的增量可以是 6（包括门）。新的当前源审计在受支持的自动 main/PR 配置文件中总共有 71 个潜在自托管非 Node 行。该保守联合包括 5 个 core-lint 行、5 个 core-type 行、5 个 Windows 行和 13 个 UI E2E 行；它的轮廓最大值并不全部共存。六个扩展 lint 行保持托管状态。

保留 84 行非 Node 配额，在该并集之上保留 13 行。具有不变的 70/130 Node 上限和四个 main/21-PR 到达信封，`4 × (70 + 84) + 21 × (130 + 84) = 5,110`。这使得 890 人低于报告的每 5 分钟 10,000 人的注册限制 6,000 人的运营目标。这取代了过时的历史 `80 + 3 + 1` 解释，无需花费净空或更改矩阵上限。 Manual/frozen 发布作业和其他工作流程不在此有条件到达范围内；它没有建立完整的组织范围内的使用。

## <a id="compiler-planning-queue"></a> 编译器规划队列

10 月 15 日分批后队列在 type/lint 入场之前仍然显示单独的铁匠队列。在 PR 库同时包含 `908efae6fe8b` 和 `9915d01d074a` 的前三个分配的规划器中，创建到开始等待的中位数为 559 秒，p75 为 637 秒。两个完成的规划器分别用了 113 和 151 秒。这些是不完整的自然运行观察，而不是整个工作流程加速测量。

同一存储库混合PR因此第一次尝试使用托管`check-plan`与其现有的串行发现模式。当前源重播在两种模式下都产生了相同的完整计划：批量发现16.7秒数和串行时间87.7在同一台 Mac 上几秒钟；最大限度RSS从16.5 GB to 5.65 GB. A Node 24.21.0 Linux重播也返回了相同的计划225秒下硬二CPU， 7-GiB限制无交换。它重复使用了相同的固定本机编译器ARM64； GitHubx64 延迟仍未测量。这些本地测量建立了执行权衡，而不是托管作业延迟。完整的图形验证器和所有compiler/lint执行所有者保持不变。在现有的可选卸载之前保留额外的强制托管行40-行阈值和45- 行限制。

## <a id="ratchet-admission-and-node-tests"></a> 棘轮准入和Node测试

选定的基线棘轮和 Node 行在预检后独立启动。最后一道门仍然需要每个选定的棘轮才能通过。这保留了着陆的平行进入路径，并避免将棘轮设置移动到飞行前。

五个最新的阔绿色 PR 在 9 月 26 日采样截止点（`36208949888`、`36208857347`、`36208617238`、`36208552952` 和 `36208291831`）在托管 `checks-fast-baseline-ratchets` 中运行了 148-173 秒。结帐耗时 31-33 秒，依赖项设置耗时 27-52 秒，棘轮耗时 73-111 秒。那些历史 Node 行正在等待这项作业。当前的 Node 行从其旁边开始。预检耗时 89-120 秒，其中包括 48-83 秒的舱单规划；这些混合运行已经跳过了预检的精确依赖关系恢复。

同一存储库混合 PR 首次尝试、自动主运行和承认的资格派遣现在要求现有的铁匠 4 级进行棘轮工作。接近默认值 - Blacksmith 运行 `36208877388` 和 `36209067188` 测量完成棘轮工作分别为 85 秒和 91 秒。他们的设置时间为 12-15 秒，逐步调整时间为 39-40 秒。这些不同头部的观察结果预计棘轮墙要少 57-88 秒；它们并不能证明当前整个工作流程的节省。

使用较慢的 91 秒观察，该路线最多为每次符合条件的运行添加建模的 `4 × 91 / 60 = 6.07` Blacksmith vCPU 分钟。它不增加任何工作岗位和一个实际的混合铁匠注册。该作业已属于默认后端下的潜在自托管非 Node 联合，因此现有的 84 行配额和 5,110 注册信封保持不变。托管路由仍适用于 GitHub 覆盖、混合重试、普通手动或冻结目标以及上游以外的存储库。棘轮检查、合并树验证、并行 Node 准入、依赖性协调和截止日期均未更改。

在单独的 `check-plan` 先决条件中，相同的五次运行花费了 165-209 秒。其编译器库存查询占用了 93-154 秒的实现步骤的大部分时间；每个缩小的 type/lint 行都会等待该结果。这些运行的中央测试类型检查在工作流程启动后 629-667 秒完成，因此仅推进 Node 准入无法满足 10 分钟 PR 目标。

因此，`check-plan` 在相同的混合准入下使用现有的 4 类，仅恢复实际自托管运行器上符合条件的相同存储库作业的确切依赖关系。该路线在现有的非 Node 储备中增加了一名铁匠注册。保留完整观察的 209 秒托管墙作为其保守的成本估算会增加 13.93 vCPU 分钟，或使用棘轮估算增加 20 vCPU 分钟。在此成本范围内不假设规划器加速。原生证明必须建立物化和全流程墙；编译器覆盖范围、选定的图表和所有托管后备保持不变。

广泛后备 PR 资格不选择 `check-plan`。其观察到的墙可以验证宽 Node 路径，但无法建立新的窄 type/lint 关键路径改进。该声明需要单独的本机运行，其更改文件计划选择此先决条件。

这两个控制作业更改仅适用于混合后端。 RunsOn 保留托管棘轮和检查计划，包括资格派遣。

选择加入的 `runson` 配置文件源自混合，并将三个 `core-runtime-cron-parallel-*` 子项提取到 `c8i.8xlarge` 上的一项串行作业中：32 个 vCPU、64 个 GiB、RAM、`ubuntu24-full-x64` 和 80 个 GB gp3 根。在保留的 cron 比较清单中，所有 258 个文件都保留了其两名工人的工作和组上限，并且源 Blacksmith 工作保留了其其他子项。 RunsOn 在添加其 cron 行之前继承了 Hybrid 当前的拆分和打包。当前库存数量和定价记录在 [ 测量紧凑包装 ](/ci/routing-costs#measured-compact-packing) 中；早期固定的朝九晚四的预测并不是普遍的结果。试点的 8 个工作人员、156 秒的 cron 墙仍然是历史背景，而下面完整的两个工作人员比较拥有可用的提供商证据。

最终实例终止未经独立验证，因此 417 秒不是完整的计费生命周期。添加拆卸、存储、网络和控制平面费用。 $1.49936/小时按需参考仍然是 9 月 17 日的历史报价；在此资格认证中没有观察到按需回退。如果没有回退和中断频率，则不会声称预期的混合速率。早期大约 $0.09 的样本并不是固定的工作价格。

本机 [ 中断恢复 ](https://runs-on.com/docs/runners/labels/#retry) 仍然是未来的一个选项，需要测量裕度。 RunsOn [v3.3 允许两次自动重新运行 ](https://runs-on.com/changelog/v3.3.0/) 和 `retry=when-interrupted`：它等待整个工作流尝试完成，然后重新运行失败的作业和依赖项。新推出的恢复容量是按需的，但 GitHub 可以分配现有的匹配 Spot 运行器。因此，入场必须考虑 `first-attempt completion + retry delays + both failed/dependent replays <= 900s`；仅仅将作业置于关键路径之外是不够的。 720 秒的第一次尝试还剩下 180 秒，已经少于恢复调度、分配和门之前测量的 396 秒 cron 作业。

报告观察到的中断并与此记录的提供商行为分开重试尝试。无容量回退或手动请求的重新运行不是中断恢复证明。在完全恢复适合原始墙壁之前，选择加入配置文件会保持自动中断重试禁用状态，并且不会提出中断安全 900 秒声明。

## <a id="measured-compact-packing"></a> 实测紧凑包装

混合布局重用 [ 容量定价工作 ](https://github.com/openclaw/openclaw/pull/155277) 中的共享工具估算器。它通过 `readToolingFileTimings` 读取提交的 Blacksmith 文件测量值，并将它们传递给现有估计器的可选文件映射参数。只有这个混合放置通道才会消耗额外的地图； RunsOn继承了混合计划。更广泛的定时有效负载和全局定价系数保持不变，因此该路线不会创建竞争性文件价格表。

当一个声明的工具文件、一个传递文件摘要、一个持续时间、匹配的报告者身份和成功退出一致时，共享收集器接受完整的单例调用持续时间。本机文件摘要保留优先级。六个单例文件价格是根据三个失败的工作流程中成功的作业和子项进行修改的；第七个保持在所有者 15% 的阈值内。七个范围内的本机 Testbox 文件更新填补了缺失的合格价格并更正了供应估算。失败的工作流程和取消的租赁清理永远不会提供完整的库存或修剪证据。

Packing 允许连续的 Blacksmith 8 级工作，现有的两人上限、编号的工具子项以及没有运行时构建先决条件。每个孩子都需要 **完整的每个文件测量或精确的完整孩子本机观察** ，然后才能获得额外的打包工作。对于未知文件的默认两秒提示不能满足该要求。不完全衡量的工作保留其原始成员资格并获得其保守的报价成本和设置津贴。

完整的打包估计是 **60 秒的设置加上现有所有者工作价格和标准组价格之和中的较大者**，保留兼容的本机子观察作为下限。原生墙地板不会因工人比例而打折；共享文件估计器保持其正常的工人感知计算。每个包装作业必须适合 **720 秒，包括设置**，保留完整的孩子及其顺序，尊重兄弟姐妹家庭的分离并遵守其最后期限。较高的所有者价格不能被更快的历史样本所取代。

四个新的主要工具测试改变了早期的选择器。现在，同一估算器会对更改后的库存进行定价，而不是禁用包装批发。只有缺乏完整文件或本地证据的受影响作业才会被排除在合并之外。本机观察绑定到执行的配置、环境、有序选择器、子名称和构建模式；父计时密钥仍然是出处，而不是准入权限。因此，当同级发生更改时，未更改的子级可以保留其观察，而更改后的已执行合约会安全地使旧观察过期。

具有多个子项的合格串行工具作业拆分超过 **600 秒整墙估计**。完整的本地儿童总数在可用时推动了这一决定，而现有的工作预测仍然是一个下限；否则，标准估算将提供儿童费用。包装仍保留任何更高的标准价格。精确观察到的关键对也会分裂。运行时准备仅保留在需要的子级上，并且新分割的关键行无法通过该通道重新打包或收取另一个设置费用。 703 秒的 CLI 预测仍然是一个未解决的不可分割的尾巴。
