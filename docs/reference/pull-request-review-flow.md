本页说明你在打开或更新 OpenClaw pull request 后的评审流程：Barnacle 和 ClawSweeper 会做什么，如何根据它们的反馈改进 PR，以及当自动化保持沉默时该检查什么。

Barnacle 和 ClawSweeper 帮助维护者保持评审队列可用。它们不能取代维护者的判断。

## Barnacle

Barnacle 是确定性的 GitHub 分诊工具。它会查找已知的队列管理
场景，并通过标签、评论或关闭来做出响应。

Barnacle 可能会在以下情况下采取行动：

- PR 正文大多为空，或缺少问题背景；
- PR 没有有用的证据；
- 仅文档、仅测试、仅重构、仅 CI，或仅基础设施的更改缺少
  已链接的维护者上下文；
- 某项更改看起来更适合放在 ClawHub 或某个插件中，而不是核心中；
- 某个分支包含无关工作；
- 作者有超过 20 个打开的 PR。

Barnacle 运行于受信任的仓库工作流代码中。它不会检出或
运行贡献者代码。

大多数路由标签都是维护者或自动化信号，因此贡献者
不需要自己添加标签。

## ClawSweeper

ClawSweeper 是 OpenClaw 仓库的 AI 辅助审查和维护机器人。它可以审查 PR、评估证明、留下持久的审查评论，并帮助维护者执行受保护的修复或自动合并流程。

ClawSweeper 的积极结果只是支持性证据，不代表维护者批准。维护者仍然决定 PR 是否以及何时准备好合并。

ClawSweeper 采用队列机制。打开 PR、推送提交或添加审查请求后，不要期待立即收到响应。ClawSweeper 运行后的标签更新也可能需要一些时间。

新 PR 会进入 ClawSweeper 审查队列。维护者也可以通过标签或命令将审查、修复或自动合并流程加入队列。对于普通贡献者的更新，只有在你更新了分支、PR 描述、证明或代码之后，才应请求 ClawSweeper 再次审查。然后通过新的 PR 评论请求一次新的审查：

```text
@clawsweeper re-review
```

PR 作者也可以使用 `@clawsweeper re-run`；具有仓库写权限的用户可以对任何开放项使用这两个命令中的任意一个。直接的 `@clawsweeper review` 命令仅限维护者使用。请耐心等待：在所请求的更改尚未出现之前再次请求，只会增加队列噪音。

当 ClawSweeper 留下审查对话时，请将其视为普通的审查反馈，并使用下面的后续检查清单。

如果人类贡献者或维护者已经接管了 PR 并正在积极处理它，不要在同一时间召唤 ClawSweeper 或以其他方式处理该 PR。先让人类的审查或修复完成。如果活动停止，请检查作者是否被要求提供证明或进行其他更新。

## 在审查期间改进 PR

一旦 Barnacle、ClawSweeper 或维护者作出回应，请将该反馈作为该 PR 的下一步检查清单。

1. 阅读 ClawSweeper 的 `Rank-up moves:` 和 `Proof guidance:`，将其作为该 PR 的行动清单。评分和标签只是审查信号，不是固定的合并目标。
2. 推送所请求的代码或文档变更，并在问题、解决方案、用户影响或证据发生变化时更新 PR 描述。
3. 使用与变更相匹配的证据，补充所请求的证明材料。
4. 自行解决已处理的审查对话。只有在你需要维护者或审查者判断时，才回复并保留对话处于打开状态。
5. 仅在分支、PR 描述、证据以及相关 CI 结果都已更新后，再请求重新审查。作者、维护者和 ClawSweeper 之间进行多轮更新与审查循环是正常的。
6. 尽可能将讨论留在 PR 中。只有在 PR 需要维护者协调、自动化似乎被阻塞，或下一步决定难以在 GitHub 评论中达成一致时，才转到 Discord 的 `#clawtributors`。请附上 PR 链接、当前状态，以及具体问题或尚需补充的证据。

请保持 PR 正文为最新状态。评论有助于讨论，但 PR 描述才是维护者和自动化会反复查看的持久摘要。

`status: ⏳ waiting on author` 表示下一步动作在 PR 作者这边：在请求再次审查之前，先更新分支、PR 描述、证明材料，或补充缺失的上下文。

有用的证据包括聚焦的测试输出、CI 结果、截图、录屏、终端输出、现场观察、已脱敏日志或工件链接。对于视觉变更，尽可能在适当时提供变更前后截图。对于证明文件，优先链接 CI 工件、GitHub 上传的截图或录屏，或一小段已脱敏的日志摘录。除非这些内容本身就是文档、测试或产品变更的一部分，否则不要提交生成的证明文件。

脱敏敏感数据是贡献者的责任。在发布证据前，请移除密钥、令牌、私有 URL、用户数据以及无关日志。

OpenClaw 还使用单独的 stale 自动化。未分配的 issue 和 PR 在 14 天无活动后可能被标记为 stale，再过 7 天无活动后关闭。已分配的 PR 会在打开 27 天后被标记为 stale，无论之后是否有更新；若在 stale 后 7 天内仍无活动，则会关闭。如果已分配的 PR 仍在活跃推进中，请与正在处理它的维护者协调。

## 当自动化保持静默时

当维护者已经在处理该事项、某个审查或修复请求仍在队列中、事件属于常规情况，或者 ClawSweeper 处理通道未配置所请求的操作时，自动化可能会保持静默。

当某个受信任的工作流需要运行不受信任的贡献者代码时，它也可能不会采取行动。在这种情况下，维护者会改用常规审查或更安全的工作流。

## 故障排查

如果 ClawSweeper 没有立即响应，请在重试前等待。该服务是
基于队列的，反复添加评论或更改标签可能会让该线程更难
审查，而不会让队列更快。

在寻求帮助之前，请检查：

- PR 描述是最新的；
- 最新提交包含所请求的更改；
- CI 已完成，或者 PR 正文解释了任何仍然存在的失败为何
  与该 PR 无关；
- 最新的审查请求是作为 PR 评论发出的：
  `@clawsweeper re-review`；
- 维护者或贡献者并未已经在积极处理该 PR；
- 最新请求尚未仍处于 ClawSweeper 的正常队列延迟时间内。

如果在 PR 更新为最新内容后数小时内仍然没有 ClawSweeper 的响应，
或者如果 PR 似乎被自动化流程阻塞，请在 Discord 的 `#clawtributors` 中提问。
请包含 PR 链接、你的预期、你何时提出请求，以及自上次机器人评论以来
发生了什么变化。
