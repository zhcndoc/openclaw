## <a id="release-checks-stages"></a> 发布检查阶段

`OpenClaw Release Checks` 是最大的子工作流程。它解析一次目标并验证伞的共享包工件（如果可用）。当包或 Docker- 面向阶段需要时，直接或集中调度会准备自己的 `release-package-under-test` 工件。

| 阶段                    | 细节                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 发布目标           | **作业：** `Resolve target ref`<br />**支持工作流程：** 无<br />**测试：** 选定的参考，可选的预期验证SHA、轮廓、混凝土释放检查组和重点实时套件 filter.<br />**Rerun：** 选择失败表面的混凝土组。                                                                                                                                                                                                                                                                                                                                     |
| 打包神器         | **作业：** `Prepare release package artifact`<br />**备份工作流程：** 无<br />**测试：** 验证伞的不可变包元组，或打包一个direct/focused 发布检查调度的候选 tarball，然后将其公开给面向下游包的 checks.<br />**Rerun：** 受影响的包、跨 OS 或 live/E2E 组。                                                                                                                                                                                                                                                         |
| 安装烟            | **作业：** `Run install smoke`<br />**支持工作流程：** `Install Smoke`<br />**测试：** 具有根 Dockerfile 烟雾映像重用的完整安装路径， QR 软件包安装、根和网关 Docker 冒烟、安装程序 Docker 测试和 Bun 全局安装以及 CLI/local-agent/Gateway 运行时冒烟和咨询 Bun-only 运行时冒烟（冻结除外）目标）。<br />**重新运行：** `rerun_group=install-smoke`。                                                                                                                                                                                              |
| 交叉-OS                 | **作业：** `cross_os_release_checks`<br />**支持工作流程：** `OpenClaw Cross-OS Release Checks (Reusable)`<br />**测试：Linux上的**新鲜和升级通道，针对所选提供商和模式的 Windows 和 macOS，使用候选 tarball 和基准包。 Linux、Windows 和 macOS 网关安装和升级套件测试版、稳定版和完整发布，记录了 pass/fail conclusions.<br />**Rerun：** `rerun_group=cross-os`。                                                                                                                                               |
| 回购并上线 E2E        | **作业：** `Run repo/live E2E validation`<br />**支持工作流程：** `OpenClaw Live And E2E Checks (Reusable)`<br />**测试：**存储库E2E，实时缓存， OpenAI websocket 流、本机实时提供程序和插件分片，以及由 `release_profile`.<br />**Runs 选择的 Docker- 支持的实时 model/backend/gateway harness：** `run_release_soak=true`、`release_profile=full` 或聚焦`rerun_group=live-e2e`.<br />**重新运行：** `rerun_group=live-e2e`，可选用`live_suite_filter`。                                                                                                         |
| Docker 发布路径      | **作业：** `Run Docker release-path validation`<br />**支持工作流程：** `OpenClaw Live And E2E Checks (Reusable)`<br />**测试：** 针对共享的发布路径 Docker 块包 artifact.<br />**Runs：** `run_release_soak=true`、`release_profile=full` 或聚焦 `rerun_group=live-e2e`.<br />**Rerun：** `rerun_group=live-e2e`。                                                                                                                                                                                                                                                              |
| 包裹验收       | **作业：** `Run package acceptance`<br />**支持工作流程：** `Package Acceptance`<br />**测试：** 离线插件包固定装置、插件更新和已发布的升级幸存者检查压缩包。标准模拟 OpenAI Telegram 包 E2E 被推迟到 beta `all`，无需浸泡；显式 `package` 并默认选择它。阻止发布检查使用默认的最新发布的基线；浸泡检查 （`run_release_soak=true`） 一次性解析最新的稳定基线，然后针对 it.<br />**Rerun：** `rerun_group=package` 运行报告的问题升级装置。 |
| 成熟度记分卡       | **作业：** `Render maturity scorecard release docs`<br />**支持工作流程：** `maturity-scorecard.yml`<br />**测试：** 根据目标参考呈现咨询成熟度记分卡文档。仅当 `run_maturity_scorecard=true` 为 passed.<br />**时运行重新运行：** 直接手动 `rerun_group=qa` 和 `run_maturity_scorecard=true`。                                                                                                                                                                                                                                                                      |
| QA 奇偶校验                | **作业：** `Run QA Lab parity lane` 和 `Run QA Lab parity report`<br />**支持工作流程：** 直接作业<br />**测试：** 候选和基线代理奇偶校验包，则奇偶校验为 report.<br />**Rerun：** `rerun_group=qa-parity`；直接手动子调度可以与 `qa` 聚合。                                                                                                                                                                                                                                                                                                                |
| QA 运行时奇偶校验        | **作业：** `Verify QA Lab runtime-pair lanes`<br />**后台工作流程：**直接作业<br />**测试：**标准核心`openclaw`/`codex`车道（`pnpm openclaw qa suite --runtime-pair openclaw,codex --runtime-pair-lane core`） 以及 `run_release_soak=true` 浸泡通道。包括 OpenClaw 核心重启证明。发布验证器强制执行记录的lane status.<br />**Rerun：** `rerun_group=qa-parity`；直接手动子调度可以与 `qa` 聚合。                                                                                                                           |
| QA 运行时工具覆盖范围 | **工作：** `Enforce QA Lab runtime tool coverage`<br />**支持工作流程：**直接工作<br />**测试：**动态刀具漂移`openclaw`和`codex`在标准核心运行时对通道中（`pnpm openclaw qa coverage --tools`），使用该通道的输出。阻止：这项工作不是建议性的-overridable.<br />**重新运行：** `rerun_group=qa-parity`；直接手动子调度可以与`qa`。                                                                                                                                                                                             |
| QA 直播 Matrix           | **作业：** `Run QA Live Matrix catalog`<br />**支持工作流程：** `QA-Lab - All Lanes`可重用工作流程<br />**测试：** 源自目录YAML 场景通过 `qa-live-shared` 环境中的共享 Matrix 实时适配器分布在固定的 shards.<br />**Rerun：** `rerun_group=qa-live` 和 `live_suite_filter=qa-live-matrix` 上；直接手动子调度可以与 `qa` 聚合。                                                                                                                                                                                                   |
| QA 现场嗡嗡声             | **作业：** `Run QA Lab live Buzz lane`<br />**支持工作流程：** `QA-Lab - All Lanes`可重用工作流程<br />**测试：**签名金丝雀和使用专用凸租用身份和托管中继 room.<br />**Rerun：** `rerun_group=qa-live` 和 `live_suite_filter=qa-live-buzz` 通过真正的 Buzz 插件进行提及门控往返；直接手动子调度可以与 `qa` 聚合。                                                                                                                                                                                                      |
| QA 直播 Telegram         | **作业：** `Run QA Lab live Telegram lane`<br />**支持工作流程：** 受信任 `OpenClaw Release Telegram QA` 调度 <br />**测试：** 直播Telegram QA，带有凸 CI 凭证 leases.<br />**重新运行：** `rerun_group=qa-live`；直接手动子调度可以与 `qa` 聚合。                                                                                                                                                                                                                                                                                                                        |
| QA 直播 Discord          | **作业：** `Run QA Lab live Discord lane`<br />**支持工作流程：** 直接作业，其状态由发布验证程序强制执行<br />**测试：** 实时当 `OPENCLAW_RELEASE_QA_DISCORD_LIVE_CI_ENABLED` 为 enabled.<br />**时，Discord QA 与凸 CI 凭证租赁重新运行：** `rerun_group=qa-live` 与 `live_suite_filter=qa-live-discord`。                                                                                                                                                                                                                                                        |
| QA 直播 WhatsApp         | **作业：** `Run QA Lab live WhatsApp lane`<br />**支持工作流程：** 直接作业，其状态由发布验证程序强制执行<br />**测试：** 实时当 `OPENCLAW_RELEASE_QA_WHATSAPP_LIVE_CI_ENABLED` 为 enabled.<br />**时，WhatsApp QA 与凸 CI 凭证租赁重新运行：** `rerun_group=qa-live` 与 `live_suite_filter=qa-live-whatsapp`。                                                                                                                                                                                                                                                    |
| QA 直播 Slack            | **作业：** `Run QA Lab live Slack lane`<br />**支持工作流程：** 直接作业，其状态由发布验证程序强制执行<br />**测试：** 实时当 `OPENCLAW_RELEASE_QA_SLACK_LIVE_CI_ENABLED` 为 enabled.<br />**时，Slack QA 与凸 CI 凭证租赁重新运行：** `rerun_group=qa-live` 与 `live_suite_filter=qa-live-slack`。                                                                                                                                                                                                                                                                |
| 发布验证者         | **作业：** `Verify release checks`<br />**后备工作流程：** 无<br />**测试：** 所选重新运行所需的发布检查作业group.<br />**Rerun：** 在焦点子作业通过后重新运行。                                                                                                                                                                                                                                                                                                                                                                                                            |

## <a id="docker-release-path-chunks"></a> Docker 发布路径分片

当 `live_suite_filter` 为空时，Docker 发布路径阶段会运行这些分片：

| 分片                                                           | 覆盖范围                                                                                                                                    |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `core`                                                          | Core Docker 发布路径冒烟测试通道。                                                                                                       |
| `package-update-openai`                                         | OpenAI 软件包和工具调用证明、Codex 按需安装和实时进度、根管理的 VPS 升级以及经过身份验证的更新重启。 |
| `package-update-onboarding`                                     | 频道加入、安装切换和技能安装。                                                                              |
| `package-update-migrations`                                     | 渠道切换和发布包升级生存。                                                                                   |
| `package-update-self-upgrade`                                   | 本地升级生存以及与发布的 9 月更新驱动程序的兼容性。                                                           |
| `plugins-runtime-plugins`                                       | 运行插件行为的插件运行时通道。                                                                                         |
| `plugins-runtime-services`                                      | 基于服务和实时插件的运行时通道。                                                                                               |
| `plugins-runtime-install-a` 至 `plugins-runtime-install-h` | 插件 install/runtime 批量拆分以进行并行发布验证。                                                                       |
| `openwebui`                                                     | 请求时在专用大磁盘 runner 上隔离运行的 OpenWebUI 兼容性冒烟测试。                                                     |

所有 package/update 行在每个发布配置文件中保留其覆盖范围。通过多个已发布的基线，`package-update-migrations` 可扩展为每个基线一项通道切换作业和一项独立升级作业。每个作业都重复使用确切的候选包和图像，保留现有的加权 npm 限制，并上传单独的分片工件。这可以避免在一个运行程序的 npm 池后面序列化所有已发布的升级，而不会增加每台主机的并发性。 `package-update-core` 和 `package-update` 保留聚合手动块名称。根管理的 VPS 升级和经过身份验证的重新启动检查在 OpenAI 行中运行。缺少所需的凭据仍然会导致工作失败；诊断池继续进行，因此独立的非实时检查也会报告其结果。设置失败和取消不会启动该池。

扩展的已发布升级幸存者和更新迁移覆盖范围在特定于基线的隔离场景作业中运行，每个矩阵最多有 32 个活动的目标 Docker 作业。在场景扩展之前允许长独立 restart/auth、插件更新和根管理的升级作业；固定的基线群组从最新的开始。分组和执行规划器共享相同的基线兼容性规则；包标识、新场景容器、每个运行者 npm 限制和故障报告保持不变。

当只有一个 Docker 通道出现故障时，在可重复使用的 live/E2E 工作流程上使用目标 `docker_lanes=<lane[,lane]>`。发布工件包括每通道重新运行命令以及包工件和映像重用输入（如果可用）。
